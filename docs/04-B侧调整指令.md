## 2. 改 cubicasa 路由（P0，`agent/engine_adapter.py`）

原则：**洁具和门窗由 engine 给出数字，不再让 Gemini 计数；Gemini 只回答房间类问题；厨房用先验。**

engine 返回结果里的 `method` 字段已经标明了来源，adapter 按它分流就行：

```python
from engine import answer as engine_answer, cubicasa

ROOM_CATS = {"floors", "sauna", "bedroom", "bathroom", "wc_room", "balcony"}

def answer_from_engine(path, question):
    r = engine_answer.answer(path, question)
    m = r.get("method", "")
    if m.startswith("cubicasa:vlm[yolo"):            # YOLO 结果：直接采用，不再调用 Gemini 计数
        r["source"] = "detector"
    elif m.startswith("cubicasa:prior:kitchen"):      # 厨房：先验 96%，比 Gemini 准
        r["source"] = "prior"
    elif m.startswith("cubicasa:") and cubicasa.category(question) in ROOM_CATS:
        r["source"] = "needs_vision"                   # 告诉 agent：这一题去调 count_in_drawing（Gemini）
    elif m.startswith(("swiss_dxf:", "ifc:")):
        r["source"] = "geometry"
    return r
```

在 agent 的系统提示词里加一句：
> `answer_from_engine` 返回的 `source` 是 `detector`、`prior` 或 `geometry` 时，直接用它的 `value`，不要再调用 `count_in_drawing`；只有 `source == "needs_vision"` 时才调用 `count_in_drawing`。

前端：`items[].png_bbox` 是 PNG 的像素坐标 `[x0, y0, x1, y1]`，直接画橙色编号框，和 swiss 的处理方式一样。

## 3. Nemotron 改为“一致性徽章”（P1）

现状：Nemotron 复核栅格图计数，结果是绿/黄徽章。改成：

| 情况 | 徽章 | 显示的答案 |
| --- | --- | --- |
| Nemotron 计数 = engine 计数 | 绿色 “2 independent methods agree” | engine 的值 |
| 不一致 | 黄色 “methods disagree – check boxes” | **仍然是 engine 的值**，同时显示 Nemotron 的数，以及两边的框 |
| 题目来源是 geometry（swiss/IFC） | 灰色 “exact from geometry” | 不调用 Nemotron，省下成本 |

**不要用 Nemotron 的数覆盖答案。** 数据显示，两边不一致时检测模型答对的次数是 VLM 的 3–8 倍。

## 10. 新增：结构化接口，应对评委换问法（P0）

**问题**：`engine.answer(path, question)` 靠题库的固定句式识别问题。评委问 "toilets on this floor?" 或 "how many WCs" 时会识别失败，退回到大模型去猜。

**解决**：新增 `engine/query.py`，让 Gemini 只负责把问题翻译成参数，数字仍由 engine 精确计算。

| 函数 | 作用 |
| --- | --- |
| `inventory(path)` | 返回这张图支持哪些类别、哪些范围，以及**图纸原文的房间标签**（Küche、Bain、ESIK…）、楼层名、户号、房间列表 |
| `query(path, intent, category, scope)` | 返回值和 `answer()` 相同，另外多出 `interpreted`（引擎是怎么理解这道题的）和 `canonical_question` |

**验证**：从题库三个来源各抽 1,500 题，先拆成参数再交给 `query()`，结果和 `answer()` **4,500 题全部一致**，所以准确率就等于全量评测的准确率。

**局限（已经内置处理）**：
- 不支持的组合（例如“某个房间里有几个马桶”、扫描图的面积）一律返回 `value=None` 并说明原因，**不会猜一个数**。
- 类别同义词统一映射：WC、toilet、toilets 都映射到 `toilet`。认不出的类别直接拒答。
- 标签必须用图纸原文，从 `inventory()` 返回的 `room_labels` 里选。不要自己翻译，比如 "Kitchen" 匹配不上图上的 "Küche"。
- 一个名称对应多个房间时（例如 4 个 Bad），面积返回合计加逐项明细，不替用户挑其中一个。
- 改写问法的正确率由 B 侧抽测，建议准备 30 个改写问题。engine 只保证从参数到答案这一段是对的。

> For counts and measurements, call `drawing_query`. Map the user's wording to the canonical category (WC → toilet, washbasin → sink). ## 11. 面积题证据字段（evidence）

swiss 和 IFC 的面积、长度、体积答案新增 `evidence` 字段。trace 面板应直接展示这个字段，评委可以手算核对。

```json
"evidence": {
  "formula": "17.29 (1.02 Zimmer) + 4.93 (1.03 Bad) + … = 118.32 m²",
  "rule": "sum of rooms whose number lies inside the apartment outline, minus outdoor spaces, …",
  "breakdown": [{"number": "2.42", "name": "Treppenhaus", "area_m2": 14.04,
                 "gross_area_m2": 16.87, "holes": [{"area_m2": 2.83, "number": null}],
                 "net_formula": "16.87 - 2.83 = 14.04 m²",
                 "png_polygon": [[x, y], …], "pdf_polygon_pt": [[x, y], …]}],
  "excluded": [{"number": "1.01", "name": "Balkon", "area_m2": 5.6, "reason": "outdoor (name)",
                "png_polygon": […]}]
}
```

展示建议：
- `breakdown` 的多边形用绿色半透明填充，`excluded` 用灰色斜线填充，悬停时显示 `reason`；
- 面板顶部放 `formula`，有孔洞的房间额外显示 `net_formula`。

IFC 的 `breakdown` 每项带 GlobalId，可以在 IFC 查看器里定位。

排除规则：
- **室外**：按名字判断，或 PNG 填色 < 235；
- **公共区域**：填色 < 247，只在户型面积里排除；
- **楼梯和电梯**：只在户型面积里排除；
- **竖井**：按名字判断；
- **孔洞**：房间轮廓内最外层的内轮廓。

PNG 读不到时，退回到只按名字判断，并在 `warnings` 里写明。

## 12. 房间检测模型和零 API 模式（cubicasa）

- 新增模型 `models/cubicasa_rooms_yolo11m.pt`（39 MB）和配置 `models/rooms.json`。**合并时这两个文件必须一起拉下来**。
- `detector.detect(png, "rooms.json")` 运行房间模型，原来的 `detector.detect(png)` 仍然运行门窗洁具模型。两者都需要 ultralytics。

**每个类别用哪个来源**，按测试集结果选定，写在 `engine/cubicasa.py` 的 `SOURCE_WITH_VLM` 和 `SOURCE_NO_VLM` 里：

| 类别 | 有 VLM 时 | 零 API 时 |
|---|---|---|
| 门、窗、马桶、洗手池、淋浴/浴缸 | 检测模型 | 检测模型 |
| 卧室 | 房间模型 87.5% | 房间模型 87.5% |
| 阳台、楼层数、WC 房间、桑拿、浴室 | VLM | 房间模型（浴室用先验） |
| 厨房 | 先验 95.6% | 先验 95.6% |

cubicasa 测试集整体：**有 VLM 时 83.57%**，**零 API 时 79.90%**（不调用任何外部 API，单题成本约为 0）。

**开关**：设置环境变量 `JUNCTION_NO_VLM=1` 进入零 API 模式。演示成本分时可以现场切换，对比两种模式。

**method 字符串有变化**：
- `cubicasa:vlm[yolo-cubicasa]:*` 改为 `cubicasa:detector[yolo-cubicasa]:*`；
- 新增 `cubicasa:rooms[yolo-cubicasa-rooms]:*`。

零 API 模式下，`warnings` 里会带一句 `zero-API mode`。
