## 2. What changed for you (interface)

### 2.1 Every answer now has `confidence` and `confidence_reason`

```json
{"value": 7, "unit": "count", "method": "cubicasa:detector[yolo-cubicasa]:window",
 "confidence": "low", "confidence_reason": "object detector; correct on 57% of held-out CubiCasa test questions of this kind", ...}
```

- Levels: `high`, `medium`, `low`, `none` (no value; the reason says why).
- Applies to `engine.answer.answer`, `answer_sheet`, `engine.project.answer` and `/ask`. A project answer takes the
  lowest level of the sheets it combined.
- After `/review` the answer becomes `confidence: "high"`, reason "checked and corrected by a person".
- It is calibrated. On CubiCasa test questions, answers marked high are correct 95.7 % of the time (8,980), medium 81.1 % (5,684) and low 56.7 % (2,030).
  Swiss and IFC answers are high (100 % / 99.3 %).
- **Frontend suggestion:** show a colour chip (high green, medium amber, low red), put the reason in a tooltip, and
  sort the review list low first.

### 2.2 `answer_sheet(path, question, page=None)`

- `page` is 1-based and means the same as the `file.pdf#pN` suffix. If both are given, the suffix wins.
- `/ask` with `{"path": "...", "page": 3, "question": "..."}` works too.
- **Breaking only if you called it positionally with a 3rd argument:** the old 3rd argument `source` is now a keyword.

### 2.3 New IFC routes (handoff 38 items 1–3)

All routes take `path` under `data/` or `uploads/` (same rules as `/ask`). `space_model` (optional) = another IFC of the
same project that holds the rooms, e.g. the architectural model when fixtures are in the plumbing model.

| route | input | output |
|---|---|---|
| `GET /ifc/storeys?path=` | | `{"storeys": [{"guid","name","elevation_m","height_m","bbox","space_count"}]}` |
| `GET /ifc/spaces?path=` | | `{"spaces": [{"guid","name_raw","long_name","storey_guid","storey_name","elevation_m","height_m","area_m2","polygon","label_point","bbox","outline"}]}` |
| `POST /ifc/room_of` | `{"path","guids":[...],"space_model"?}` | `{"rooms": {guid: {"space_guid","space_name","method":"rel-contained|point-in-polygon","storey_name"}}}` |
| `POST /ifc/clearances` | `{"path","guid","space_model"?}` | see below |

Python, if you call the engine directly: `engine.ifc_geom.storeys / spaces / room_of / clearances / north`.

**Coordinates:** web-ifc world, metres, Y up: `(X, Y, Z) = (x_ifc, z_ifc, -y_ifc)`.

- `polygon` is `[X, Z]` on the floor plane.
- `label_point` is `[X, Y, Z]`, always inside the polygon (checked 208/208).
- `bbox` is `[[min], [max]]`.
- `outline` says how the room shape was obtained: `"profile"` means the exact room outline from the model; `"convex hull of the body"` is the fallback.
- If your viewer uses web-ifc `COORDINATE_TO_ORIGIN`, add that offset yourself. We do not apply it. Please tell us whether you use it.

**Clearances (renovation distances):**

```json
{"guid": "...", "room_guid": "...", "north_basis": "true_north", "exact": true,
 "method": "geometry:mesh-to-wall-face",
 "sides": [{"compass": "S", "bearing_deg": 159.9, "basis": "true_north", "dir": "left",
            "distance_m": 0.0, "wall_guid": "...", "wall_name": "...", "from": [x,y,z], "to": [x,y,z]}],
 "warnings": ["..."]}
```

- `distance_m` is the fact: the shortest plan distance from the fixture's own mesh to that wall. 0.0 means it touches the wall.
- **Direction is unified on `compass` (N/E/S/W) and `bearing_deg`** (clockwise from north). It comes from the model's TrueNorth (`basis: "true_north"`). If the model states none, north is the model's +Y (`"project_north"`, plan-up, not confirmed); show that as "plan north" in the UI.
- `dir` (front/back/left/right) is the fixture's own local axes. It is a reference only; do not use it as the main label.
- `exact: false` (with a warning) when some geometry could not be read. In that case no distance is guessed.
- Draw `from` → `to` as a dimension line in the 3D view.

### 2.4 Detector change (no code change for you)

`models/detector.json` has a new key, `suppress_nested: ["window", "shower_tub"]`. A box that lies ≥ 70 % inside a bigger box of the same class is dropped (a pane inside its window, a tub inside its shower box). The rule also applies to cached detections.

## 6. Known limits (say these honestly in the demo)

- Scans:
  - door counts can overshoot when swing arcs are faint (flagged `uncertain`, alternatives offered for review);
  - slab area by type on the sample slab plan reads one bay (30.84 m²), while a hand reading gives 61.7 m².
- Raster windows are the weakest category (57 %). The main error is adjacent windows merged into one box.
- PDFs and scans:
  - no north-arrow reading yet, so directions there are page directions;
  - a distance is given only where it is printed or after the user calibrates the scale.
- IFC outlines are convex hulls in plan, so L-shaped walls can read too close (then `exact` stays honest).
