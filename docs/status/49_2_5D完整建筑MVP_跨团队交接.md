# 49 — 2.5D 完整建筑 MVP：跨团队交接

目标不是把 2D 平面「切开」后贴到屏幕上，而是将每张已识别的图纸转成一个可阅读的 2.5D 建筑示意：外墙与室内隔断均为墙，墙、门、窗和房间的平面位置来自同一套坐标；门窗落在对应墙线上；构件落在对应房间内。MVP 的洁具使用统一示意图标即可，不承诺其精确外形或比例。

## 共同的完成定义

1. **完整性优先。** 对一个可处理楼层，外墙和所有室内隔断均渲染为连续墙网络；不因进入房间而把墙截到 1.2 m。该楼层的可视墙高统一：优先采用可信层高，否则使用 `2.7 m` 并在响应 `warnings` 标为假定显示高度。
2. **坐标唯一。** 房间 polygon、墙 centreline/footprint、opening 和 fixture 必须同一平面坐标系（X/Z metres，Y-up）。任何原点、旋转或图像→米的标定只可在引擎做一次，前端不得分别猜测偏移。
3. **可用但不伪造。** 有可靠比例的 IFC/矢量图才可标为 `measured` 并显示比例尺；未标定扫描件必须标为 `illustrative / not to scale`。不存在的管线、房间、洁具不能由前端补造。
4. **95% 的含义。** 该目标只针对输入中可识别的建筑结构：以图纸/引擎 overlay 为准，外轮廓、隔断、门窗位置覆盖至少 95% 的已识别结构；未知、低置信或图纸本身没有的信息必须明确标记为缺失，不能把它算作已吻合。
5. **交互路径。** 2D 点一个已识别房间 → 直接打开该房间的 2.5D（同一层、自动 fit）；点 Building 才打开整层/整栋概览。房间不存在有效 scene 对应项时留在 2D 并说明“该房间尚无 2.5D 几何”，不得跳到空的总览。

## Claude / 页面状态与配置（需要实现）

所有修改仍在 Claude 所有的 `web/src/gigi/RealWorkspace.tsx`、`web/src/gigi/RealPlan.tsx`、项目配置内；不要改 Codex 的 `Real3D.tsx` 或 `IsoSceneSvg.tsx`。

1. 每次切换图纸时读取本页的 `plan_rooms`，保存 `selectedPlanRoom`：`{ id, number, name, polygon_px, page, sourcePath }`。不要等用户提问后才有房间数据。
2. 在 `RealPlan` 为每个非空 `polygon_px` 画透明、可访问的点击区域（按钮语义/键盘可触发）；点击回调传整个 `selectedPlanRoom`。
3. 选择房间后设置视图为 `3d-room`，并把 `selectedPlanRoom.id`（或 `number`）作为 `focusRoomId` 传给 `Real3D`。`3d-building` 只能由用户显式点 Building 进入。
4. 选择新的 sheet、项目或返回 2D 时清空过期的 `selectedPlanRoom`；Room 的 `← Floor` 返回当前 sheet 的 2.5D Floor，不返回 Whole Building。
5. 让每个 sheet/project 可选地带 `geometryPath` 与 `spaceModel`。`geometryPath` 是 scene 读取的源；当管线 IFC 与建筑 IFC 分离时，把 `spaceModel` 一起传给 scene 请求（Duplex 是必须场景）。不得用显示名称猜文件路径。
6. 处理 scene 报错/空结构：展示后端的 `warnings` 和明确的缺失状态，保留 2D，而不是显示看似成功但空白的 2.5D。

## Xinran / 引擎与 scene 数据（需要提供）

保持现有 `/geometry/scene` / `/api/geometry/scene` 兼容；不要通过前端或 LLM 生成几何。

1. 对每个支持的 IFC/矢量图楼层输出连续的墙网络：外墙和所有内隔断，至少包含 `id`、`points` 或 `footprint`、`thickness_m`、`base_y_m`、`height_m`、`storey_id`、`confidence`、`source`。`footprint` 有值时它是非直线墙的平面真值。
2. 每个门窗输出 `wall_id`、bottom-centre `position`、`width_m`、`height_m`、`sill_y_m`、`rotation_deg`、`source`；其位置要落在对应 wall footprint/centreline 容差内。门窗朝向不是当前 MVP 阻塞项。
3. 每个 room 输出稳定 `id`、原图真实 `number/name`、polygon、label point、area、storey id、source。若原图只写 `Room 2.16`，不要擅自命名成 Bathroom；可由真实 `objects[]` 推导 UI 辅助文字 “contains toilet, bathtub, sink”。
4. 每个已识别洁具输出 `category`（至少 toilet/sink/shower/bathtub/vanity/stove）、`room_id`、position、footprint、source。前端会将类别画成统一图标，不要求精确产品形状。
5. 仅输出实际识别到的 `systems`；管道/电力/HVAC 必须带真实 `points` 和类别。没有数据就空数组与 warning。
6. 矢量 PDF 需要补齐 outline/double-line 墙和基本卫浴符号识别；扫描件未校准或未能识别房间/墙时必须是 illustrative，不能许诺实量 2.5D。
7. 给前端一份项目—sheet—geometryPath—spaceModel 的明确映射，特别是 Duplex 的 plumbing IFC + architecture IFC 配对。当前 repo 可直接读取的 `duplex_arc.ifc` 只有 vanity，不足以验证 WC/shower MVP。

## Codex 已完成的前端部分

- `IsoSceneSvg` 用同一 scene 几何画浅灰完整墙、门窗、地板与统一洁具图标；墙高按当前楼层/scene 的统一高度绘制，不再在房间视图切低。
- 房间引用不再只接受 22 位 IFC GUID；`2.16`、`room-2.16`、`RM 2.16` 可解析到同一个 scene room。
- 元素条和图标 tooltip 同时显示构件类别与可读房间说明，例如 `Toilet · Room 2.16`，避免只显示 `RM 2.08.1` 这类内部编号。
- 真实 2D 点击状态、完整 geometry 数据与 IFC 配对仍需要上述两方接入；缺其中任一项，不能诚实宣称“整套图纸 95% 自动生成”。
